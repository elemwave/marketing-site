# Scan every public page for definite accessibility failures with `@axe-core/playwright`

## Context

Verification opened some exported pages in a browser and checked a few individual controls and tokens — an accessible name here, an expanded state there, two token pairs against the Level AA contrast minimum — but nothing scanned a rendered page as a whole for contrast, landmarks, alternative text or heading order. Individual defects reached the public site more than once, each filed as its own card; fixing one did not stop the next.

## Decision

- Scan with **`@axe-core/playwright`**, driven from the existing `Browser tests` Playwright suite, rather than adding a second browser-automation dependency such as `pa11y`/`pa11y-ci`, or using Lighthouse's accessibility category. The project already depends on `@playwright/test` for that suite; axe-core enumerates rule-level violations that map directly onto named failure classes such as contrast, landmarks, alternative text and heading order, and separates definite failures from ones needing a person's judgement. Lighthouse's category is a composite score, a coarser fit for the same classes.
- Pin `@axe-core/playwright` to the **exact version `4.13.0`** in `projects/marketing/package.json`, not a caret or tilde range, matching the project's existing convention for `@playwright/test` (pinned to `1.63.0`). `@axe-core/playwright`'s own `README.md` states it does not follow semver on its minor version — it tracks `axe-core`'s own minor — so an unpinned range can add rules that start failing the gate on an unrelated `npm install`.
- Cover exactly the **six pages** the living landmark requirement already names, as a fixed list in `projects/marketing/e2e/accessibility.spec.ts`: the home page, the contact page, the partnerships page, the privacy policy, the integrated policy, and a path with no page. The site is six pages and a path with no page, so a fixed list needs no discovery mechanism. Crawling the export's sitemap or internal links was rejected as unneeded complexity that would silently start covering a future non-public utility route nothing asks for.
- Run `.analyze()` with **no `.withTags()` or `.withRules()` restriction**, so axe-core's own default rule set applies. The installed `axe-core@4.13.0` rule metadata shows `landmark-one-main` and `heading-order` carry only the `best-practice` tag, not any `wcag2a`/`wcag2aa`/`wcag21aa` tag, so restricting to those WCAG tags would silently stop checking the landmark and heading-order classes. The three rules axe ships at Level AAA (`color-contrast-enhanced`, `identical-links-same-purpose`, `meta-refresh-no-exceptions`) are each `enabled: false` in axe-core's own rule descriptor, so the unrestricted default set already excludes them without an explicit tag filter, matching the project's Level AA contrast baseline.
- Run the new spec's assertions only under the **`chromium`** Playwright project, via a `test.skip` guard inside the test body, rather than a dedicated `playwright.config.ts` project restricted by `testMatch`, or running under all four projects. These failures live in a page's structure, names and contrast, not in a particular rendering engine, so the other three projects add runtime without adding coverage; they still list the tests as skipped so a reader sees the scope rather than an absent test.
- Add the spec to the existing `projects/marketing/e2e/` directory and the existing `Browser tests` gate stage, not a new stage. `playwright.config.ts` already discovers every file under `testDir: "./e2e"`, and the `Browser tests` stage already waits on `Static export` and serves it.

## Consequences

- A first real run against the export can still turn up a failure nobody has looked for before, beyond the four classes the card's evidence named. A small, contained finding is fixed as part of making the guard pass; a finding that is not small or contained is filed as its own card rather than absorbed here.
- `color-contrast` needs a fully rendered, opaque background to resolve; where a background is an image or a gradient axe cannot resolve, the rule reports the finding under `incomplete` rather than `violations`, which this inspection does not fail the run on. None of the six covered pages currently paints body text over such a background.
- axe-core is a rule-based static-plus-computed scan. A reading-order problem invisible to its heuristics, or a screen-reader-only usability issue, can still exist behind a clean report; the inspection's guarantee is bounded to what the chosen tool reports, not to accessibility in general.
